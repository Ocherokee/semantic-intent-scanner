## Verdict

The repository is **not ready to make a v1.0 stability promise**. Its
deterministic contract implementations are unusually disciplined for a research
prototype, but the promise is not independently consumable or continuously
verified. Six issues are release blockers: formal contract publication,
URI/host normalization hardening, visible malformed-declaration semantics,
empirical detector/severity calibration with an explicit probabilistic boundary,
resource bounds for untrusted local artifacts, and CI/build/install verification.

This verdict does not require new analyzers, scoring, policy, or broader
authority. The smallest path to 1.0 is hardening and documentation around the
existing v0.9 feature set.

The classifications used below are:

- `ready`
- `needs-hardening`
- `release-blocker`
- `intentionally-experimental`
- `out-of-scope-for-1.0`

## 1. Public contract inventory

### Commands, arguments, streams, and actual exit behavior

Argparse itself exits `2` and writes usage to stderr for unknown commands,
unknown flags, and missing required arguments. That behavior is currently part
of the effective CLI even though the README does not document it.

| Command/mode | Public inputs | stdout | stderr | Actual exits |
| --- | --- | --- | --- | --- |
| `scan <path>` file | positional `path`; `--json`; `--no-color`; `--api-key` | terminal or legacy JSON report | progress; uncaught model/read errors can traceback | `0` low; `1` medium **or** missing/not-file/empty input; `2` high/critical; argparse `2` |
| `scan <path>` directory / `--dir` | same plus `--dir` | combined terminal or legacy JSON directory/semantic report | progress and detected instruction filename | `0/1/2` by worst directory/semantic risk; missing path `1`; argparse `2`; model failures are not normalized |
| `scan-remote <url>` | positional URL; `--json`; `--no-color`; `--judge`; `--api-key` | terminal or legacy remote JSON report | guarded-fetch/mode progress | `0/1/2` by risk; `3` when nothing analyzed; argparse `2`; incomplete judge coverage does not replace deterministic risk exit |
| `scan-mcp <file>` | positional file; `--json`; `--no-color`; `--judge`; `--api-key`; `--server-label` | terminal or legacy remote-shaped JSON report | captured-file/mode progress | `0/1/2` by risk; missing file `1`; malformed/no-tools `3`; argparse `2` |
| `inventory <url>` | positional HTTPS target | inventory JSON | bounded-discovery progress/errors | `0` validated artifact; `3` handled inventory error; argparse `2` |
| `inventory-diff <previous> <current>` | two JSON paths | change JSON | errors | `0` valid comparison regardless number of changes; `3` read/JSON/schema/comparison failure; argparse `2` |
| `trust-analyze <inventory>` | inventory JSON path | JSON array of finding contracts | errors | `0` valid analysis regardless findings; `3` read/JSON/schema/trust failure; argparse `2` |
| `audit` | repeatable `--directory`, `--skill`, `--remote`, `--mcp`, `--trust-inventory`; `--judge`; `--api-key`; `--server-label` | composite JSON only | invocation errors | `0` when no analyzer failed, regardless findings or incomplete semantic coverage; `3` any analyzer failure/invalid selection; argparse `2` |

Consequences for shell/CI consumers:

- Risk exits are meaningful only for `scan`, `scan-remote`, and `scan-mcp`.
- Local `scan` code `1` conflates medium findings with several invalid inputs.
- Artifact commands use `0` for a valid artifact even when changes/findings are
  present; consumers must inspect JSON.
- `audit` intentionally has no aggregate risk exit. Exit `3` signals partial or
  total analyzer failure while successful findings remain in stdout.
- Incomplete semantic/model coverage is data in reports/artifacts, not a unique
  process exit. CI can distinguish it only by parsing output.
- Unhandled model or filesystem exceptions do not have a stable documented exit
  envelope.

## 2. Formal schema readiness

No formal JSON Schema files exist. No checked-in golden complete artifacts exist
for any of the four contracts. Tests construct mappings and compare examples,
but an external consumer cannot validate an artifact independently without
installing/importing scanner code.

Most structural rules map to JSON Schema 2020-12: required fields,
`additionalProperties: false`, primitive/nested types, enums, array items, and
non-negative integer constraints. JSON itself excludes NaN and infinity, while
Python entry points must continue rejecting their non-standard decoder forms.

Supplemental semantic validation remains necessary for:

- canonical HTTPS URL equality and origin normalization;
- uniqueness by `(surface_type, resource_url)`;
- sorted arrays and canonical ordering;
- cross-record source/relationship consistency;
- change-type-dependent snapshot/path rules;
- composite execution/finding count equality;
- canonical embedded finding validation;
- normalized and bounded failure reasons.

Formal schemas are a v1.0 blocker because “stable machine-readable contract” is
otherwise scanner-implementation-dependent. They must describe current behavior,
not replace the Python validators.

**Version decision:** retain schema `0.1` at package `1.0.0` if publication and
tests merely formalize the current bytes. Bump only a schema whose compatibility
actually changes during hardening—for example, if malformed-declaration status
or a required structural locator changes an envelope. Package and schema numbers
must not be synchronized for appearance.

## 4. Exit-code contract audit

The command table above is the actual contract. Operational failure and risk are
well separated in remote/MCP, inventory, diff, trust, and composite paths. They
are not fully separated in local `scan`, where exit `1` covers both medium risk
and several invalid-input cases. `scan-mcp` also uses `1` for a missing file but
`3` for a present malformed file.

Changing these codes is not automatically required: consumers may already rely
on them. Before 1.0, pin them in tests and document the distinctions. If the
project chooses to remove a conflation, do it as one explicit pre-1.0 CLI
compatibility change with migration notes—not as incidental cleanup.

| Scheme-relative/relative declarations | resolved with `urljoin` only in supported parsers, then canonicalized | tested for manifest; not accepted by standalone canonicalizer/validated artifacts |
| Malformed hostnames | URL parser/IDNA only; `_` and percent-bearing host text were accepted by audit probe | blocker: DNS-label grammar undefined |
| IPv4/IPv6 literals | `ipaddress` compressed/canonical form; IPv6 bracketed | IPv6 form not comprehensively regression-tested in inventory/trust |
| Redirect origin | remote fetch uses a separate `_origin` tuple; default port normalized, but trailing-dot/IDNA parity with v0.6 canonicalizer is not established | port tests exist; normalization parity needs regression |

Encoded dot segments do not change origin, so no demonstrated cross-origin false
negative was found. They can, however, create distinct inventory identities for
server-equivalent paths. Malformed host acceptance and separate redirect-origin
normalization make the overall profile insufficiently specified for a 1.0 trust
boundary promise.

## 7. Structural path and provenance audit

| Analyzer | Machine-readable location retained | Gap |
| --- | --- | --- |
| Directory | file/directory path; pattern/setting and count | no line, byte offset, or exact match location; absolute vs relative path varies by finding construction |
| Semantic skill | resource path, flagged text, chunk index/excerpt when present | no line/offset; duplicate text occurrence is ambiguous |
| Remote | source/final URL, SHA, evidence text, observed time, redirect/detail metadata | no line/offset within document |
| Captured MCP | tool, friendly field, lossless `mcp_json_path`, synthetic source URI, declared unauthenticated server | strongest locator; sufficient for current accepted shapes |
| Trust manifest | source URL, target URL, origins, `api.url` or endpoint field, provenance/relationship/boundary | field is structural but not a formal JSON Pointer |
| Trust OpenAPI | source/target URL and `servers[].url` | array index is lost; multiple identical/nearby servers cannot be located exactly |

A machine can identify the resource and general structural field for every
finding, but cannot always identify the exact triggering element without text
search or prose interpretation. MCP is the exception. This is required
stabilization before promising automated remediation/retest integration, though
it is not by itself evidence that detection is wrong.

## 8. Malformed input and failure boundaries

| Surface | Current distinction | Audit finding |
| --- | --- | --- |
| Finding/inventory/change/composite artifact validation | strict required/allowed fields, enums, versions, nested shapes, non-finite rejection | strong; independent schemas missing |
| MCP capture | invalid JSON/unrecognized envelope → `invalid_input`; empty tools → `no_tools`; nameless tool entries skipped and counted | mostly explicit; whole-file and nesting resources unbounded |
| Inventory malformed JSON/XML | retrieved entry retains bounded `parse_error` metadata and no children | explicit |
| Manifest invalid declared URL/type | declaration silently ignored | release blocker |
| OpenAPI malformed `servers` entries or invalid URL | entries silently ignored; YAML marked parser unavailable | release blocker for supported JSON; YAML is an explicit unsupported boundary |
| Trust malformed/unsupported inventory | fails closed; CLI exit `3` | ready |
| Inventory diff malformed/unsupported inputs | fails closed; CLI exit `3` | ready |
| Composite adapter failure | partial artifact, explicit status, bounded normalized reason, exit `3` | ready |
| Local scan model/read failure | some invalid inputs return `1`; API and some read exceptions may traceback | needs hardening |
| Legacy CLI/inventory error text | raw exception/parser/fetch text can enter stderr/artifact fields | bound/redact before 1.0 |

Malformed content must not become an indistinguishable zero-finding success.
The manifest/OpenAPI declaration behavior violates that standard today.

## 10. Determinism audit

| Output | Safe promise | Intentional variability |
| --- | --- | --- |
| Finding serialization | Byte-identical for the same validated object; evidence array order preserved | `observed_at`, external-state detail, and model-derived content may differ across new runs |
| Inventory serialization | Stable ordering and bytes for the same validated inventory | `fetched_at`, status, final URL, hashes, redirects, live web/DNS state |
| Inventory diff | Deterministic for two identical validated input artifacts; acquisition-only `fetched_at` excluded from comparison | Input artifacts themselves may differ over time |
| Trust findings | Deterministic for one identical validated inventory | Inherits inventory acquisition differences; no network/model in analysis |
| Composite output | Deterministic ordering and repeated serialization of one artifact | Embedded finding acquisition timestamps, registry state, and model output from new executions |
| Legacy reports | Structure is stable, but report timestamps are generated at render time | current UTC timestamp and live/model state |

Nested mapping order is neutralized by sorted-key serialization where a
canonical serializer exists. Arrays are either deliberately sorted by the
producer/validator or semantically order-preserving. The safe 1.0 statement is:

> Canonical serialization is byte-stable for the same validated static object.
> New acquisition, registry/DNS, or model runs are observations and are not
> promised to reproduce identical bytes.

## 14. Experimental-boundary decisions

### Remote inventory discovery

The interface can become stable. Time-dependent observations do not make a
schema experimental. Stabilization is blocked by URI policy, malformed
declaration visibility, formal schema publication, and release CI—not by the
fact that websites change.

### Captured MCP analyzer

Stabilize only the accepted captured shapes and current string extraction:

- bare tool array;
- `{ "tools": [...] }`;
- JSON-RPC `{ "result": { "tools": [...] } }`;
- tool name, top-level description, and recursive string-valued descriptions
  under `inputSchema`;
- no `$ref` resolution, schema execution, MCP transport, server authentication,
  or tool invocation.

The accepted subset is narrow enough to promise. Future MCP protocol evolution
outside these shapes remains experimental/out of scope; the whole command need
not be labelled experimental.

### Semantic judge paths

Model-backed findings should be explicitly probabilistic/experimental for 1.0.
The deterministic lanes, append-only rule, coverage status, and failure
semantics can be stable. A model result must never erase or downgrade a
deterministic finding.

## 15. Composite audit boundary

Inventory discovery and inventory diff correctly remain outside the
`FindingContract` stream because they produce factual artifacts, not security
findings. v1.0 needs documentation only. Optional top-level factual-artifact
support may be considered later, but pseudo-findings are rejected.

v1.0 does not require composite severity, aggregate risk, a policy engine, or
deduplication.

## 16. Release classification

### A. Hard blockers for v1.0 (6)

1. Publish formal schemas, independent golden fixtures, and schema/Python drift
   tests for all four machine contracts.
2. Define and harden URI/host normalization, including IDNA, malformed hosts,
   percent encoding, encoded dot segments, IPv6, and redirect parity.
3. Make malformed supported manifest/OpenAPI authority declarations explicit;
   they must not disappear as valid zero-child observations.
4. Complete labelled-corpus false-positive/false-negative and severity
   calibration; explicitly exclude model efficacy from the stable promise.
5. Bound local skill/directory/MCP/artifact resource consumption and expose
   truncation/incomplete analysis.
6. Establish CI and clean build/install verification for the declared Python and
   OS support policy.

### B. Required stabilization work (8)

1. Freeze and fully document command-specific exit, stdout, stderr, invalid
   input, operational failure, and incomplete-coverage semantics.
2. Correct network/offline documentation for directory, MCP, and composite modes.
3. Decide and document minimum machine structural locator guarantees; improve
   missing OpenAPI/line/offset location before freezing affected contracts.
4. Normalize, bound, and redact legacy CLI/artifact failure strings.
5. Add release-level threat model, non-goals, stable/experimental labels, and
   complete resource-limit documentation.
6. Add package metadata, changelog/release notes, release mechanism, and private
   vulnerability-reporting setting verification.
7. Add public CLI/report golden tests, especially the model-backed local `scan`
   paths and every malformed invocation.
8. Update package/report/User-Agent versions deliberately in the final release
   slice while retaining independent schema versions unless their contracts
   actually change.

### C. Safe to defer to v1.1+ (8)

1. SARIF export.
2. OPA or other policy integrations.
3. Optional composite factual inventory/change attachments.
4. macOS CI if it is not part of the 1.0 support statement.
5. SLSA level advancement, signing, and provenance attestations beyond basic
   release hashes.
6. YAML OpenAPI parsing and broader schema/reference resolution.
7. Live MCP protocol support.
8. Performance optimization beyond enforcing safe resource ceilings.

### D. Explicitly rejected for v1.0 (5)

1. Composite risk or severity scoring.
2. Fuzzy or guess-based finding deduplication.
3. Autonomous execution of discovered instructions, tools, schemas, or fixes.
4. Speculative authority inference beyond supported structures.
5. Treating inventory entries or ordinary inventory changes as findings.

## 18. Proposed stabilization sequence

### v0.10 — Contract and boundary hardening

Scope:

- formal schemas and valid/invalid golden fixtures;
- URI/IDNA/percent/malformed-host policy and regressions;
- explicit malformed manifest/OpenAPI declaration coverage;
- local/MCP/artifact resource ceilings;
- structural locator minimums and bounded failure vocabulary.

Likely files/subsystems: new `schemas/` and golden fixtures,
`surface_inventory.py`, `remote_fetch.py`, finding adapters/contract only if
locator semantics change, MCP/local readers, validators, focused tests, and
versioned contract docs.

Out of scope: new analyzers, scoring, policy, execution, fuzzy deduplication,
inventory-as-finding.

Acceptance:

- schemas and Python validators agree on goldens;
- no supported malformed declaration silently disappears;
- normalization matrix is specified and tested;
- untrusted-input limits produce explicit incomplete/truncated state;
- affected schema version changes are justified individually.

### v0.11 — Empirical and operational stabilization

Scope:

- labelled deterministic corpus and severity calibration;
- protected semantic evaluation suite with experimental boundary;
- complete CLI/exit/stream/network tests and docs;
- threat model/non-goals and resource-limit documentation;
- CI matrix, package build/install, and release smoke tests.

Likely files/subsystems: fixtures/evaluation harness, report/CLI tests (behavior
changes only if explicitly approved), README/release docs, `.github/workflows/`,
and packaging metadata.

Out of scope: detector expansion, composite scoring, policy engine, SARIF/OPA,
live MCP.

Acceptance:

- calibrated deterministic results with retained misses;
- all stable paths green on declared Python/OS matrix;
- eight model tests either run in protected evaluation or are explicitly outside
  the stable gate;
- wheel/sdist clean-install and console smoke pass;
- exact public compatibility matrix published.

### 1.0.0 — Release-only slice

Scope:

- final package/report/User-Agent version decision;
- changelog/release notes and support statement;
- final clean build/install verification;
- release artifact hashes and enabled private disclosure route.

Out of scope: feature work or schema changes not forced by a discovered blocker.

Acceptance:

- every hard blocker closed with evidence;
- required stabilization checklist complete;
- full deterministic suite and release CI green;
- clean artifacts install and invoke successfully;
- working tree and tag/release commit reproducible.

## Recommendation

Do **not** call the next package release `1.0.0`. Complete v0.10 contract/boundary
hardening and v0.11 empirical/operational stabilization first. If those slices
close the six blockers without expanding scope, the following release can be a
credible `1.0.0` whose promise is stable interfaces and deterministic boundaries,
not certified detection completeness.
