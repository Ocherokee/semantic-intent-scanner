# v0.7 Inventory Baselines and Change Detection

**Status:** implemented contract

**Change schema version:** `0.1`

## 1. Purpose

v0.7 compares two already-produced, valid v0.6 inventory artifacts and reports
factual differences. The comparison does not retrieve resources, assess trust,
create findings, assign severity, or interpret whether a change is dangerous.

The data flow is deliberately offline:

```text
previous inventory + current inventory -> validation -> comparison -> change set
```

The explicit CLI is:

```text
semantic-intent inventory-diff previous.json current.json
```

It reads two local JSON files and emits deterministic JSON to stdout. It never
calls the inventory discovery or guarded-fetch paths.

## 2. Input and identity rules

Both inputs must pass the strict v0.6 inventory `0.1` validator. Unsupported
versions, unexpected fields, malformed nested values, non-finite numbers, and
duplicate identities fail closed. The two envelopes must name the same
canonical `target_origin`; comparison across different sites is rejected.

A surface identity is exactly:

```text
(surface_type, canonical resource_url)
```

The inventory validator already requires canonical HTTPS URLs. Scheme,
normalized host, effective port, path, query, and surface type therefore all
participate in identity. Fragments and equivalent aliases were removed when the
inventory was created. There is no fuzzy matching. If identities differ, the
result is one removal and one addition.

Redirect observations, provenance, relationships, and metadata are state, not
identity. Duplicate identities within either input are invalid rather than
silently merged.

## 3. Change taxonomy

| `change_type` | Compared state |
|---|---|
| `surface_added` | A current identity has no previous match. |
| `surface_removed` | A previous identity has no current match. |
| `retrieval_status_changed` | `observation.status` or `observation.http_status`. |
| `redirect_behavior_changed` | Final URL, redirect chain, or cross-origin redirect flag. |
| `content_type_changed` | Observed content type. |
| `content_digest_changed` | Two present, comparable SHA-256 digests differ. |
| `retrieval_truncation_changed` | Per-resource body truncation flag. |
| `retrieval_error_changed` | Error or blocked-reason facts. |
| `provenance_changed` | Discovery records. |
| `relationship_changed` | Declared relationships. |
| `metadata_changed` | Factual metadata object. |
| `inventory_truncation_changed` | Envelope-level 32-entry truncation state. |

Each record states only the previous and current factual values. It contains no
severity, risk, finding identifier, remediation, or security conclusion.

`fetched_at` is acquisition context, not surface state, and is intentionally not
a change trigger. Otherwise two identical scans taken at different times would
always differ. Added and removed entry snapshots also omit `fetched_at`.

A digest is comparable only when both matching entries contain `sha256`. Two
present, unequal values produce `content_digest_changed`. Present-versus-missing
does not: absence means the artifacts do not contain two content digests to
compare. It is not interpreted as compromise, safety, or evidence about why the
digest is unavailable. Retrieval-status and other observable fields continue to
be compared independently.

## 4. Canonical change contract

The envelope contains exactly:

| Field | Meaning |
|---|---|
| `change_schema_version` | Exactly `"0.1"`. Independent version domain. |
| `target_origin` | Shared canonical origin of both inputs. |
| `previous_inventory_schema_version` | Validated previous inventory version. |
| `current_inventory_schema_version` | Validated current inventory version. |
| `changes` | Deterministically sorted change records. |

Each change record contains exactly:

| Field | Meaning |
|---|---|
| `schema_version` | Exactly `"0.1"`. |
| `change_type` | One taxonomy value from section 3. |
| `surface_identity` | `{surface_type, resource_url}` for surface changes; `null` for envelope truncation. |
| `affected_paths` | Sorted JSON-style paths identifying compared fields. |
| `previous` | Previous factual value or `null` when added. |
| `current` | Current factual value or `null` when removed. |

The change schema is independent of inventory schema `0.1`, finding schema
`0.1`, scanner package version, and legacy report version. Matching numeric
labels do not imply coupled release cycles.

## 5. Determinism and mutation safety

Inputs are validated without normalization or repair, copied before comparison,
and never mutated. Entries are indexed by exact identity. Set-like discovery and
relationship arrays are compared in canonical sorted order, so input array order
does not create changes. Metadata object key order is irrelevant; metadata array
order remains factual and significant.

Changes are sorted by surface identity, change-type order, and affected paths.
Serialization uses sorted object keys, stable indentation, UTF-8 text, and
rejects NaN or infinity. Repeating a comparison produces byte-for-byte identical
output.

## 6. Examples

An added advertised endpoint is factual:

```json
{
  "schema_version": "0.1",
  "change_type": "surface_added",
  "surface_identity": {
    "surface_type": "advertised_endpoint",
    "resource_url": "https://example.com/mcp"
  },
  "affected_paths": ["entry"],
  "previous": null,
  "current": {
    "schema_version": "0.1",
    "surface_type": "advertised_endpoint",
    "resource_url": "https://example.com/mcp",
    "discovery": [
      {
        "kind": "manifest_declaration",
        "source_url": "https://example.com/.well-known/ai-plugin.json"
      }
    ],
    "observation": {
      "status": "advertised"
    },
    "relationships": [
      {
        "relationship": "declared_by",
        "resource_url": "https://example.com/.well-known/ai-plugin.json"
      }
    ],
    "metadata": {
      "endpoint_kind": "mcp_endpoint"
    }
  }
}
```

The record does not say that the endpoint is risky. Likewise, a transition from
HTTP 200 to 404 is a retrieval-status change, not a vulnerability finding.

## 7. CI and monitoring use

A CI job can retain a previously approved inventory artifact, generate or
receive a current artifact in a separate step, and run `inventory-diff` offline.
Consumers may decide which factual changes require review. That policy belongs
to the consumer, not the v0.7 comparison contract.

## 8. Explicit non-goals

No live network access, persistence service, crawler, trust-boundary analysis,
prompt-injection detection, risk scoring, finding conversion, remediation,
ethical-guardian logic, or detector/report behavior change is part of v0.7.
