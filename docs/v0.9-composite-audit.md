# v0.9: Composite Audit Orchestration

## Purpose

v0.9 adds one deterministic machine-readable envelope for running existing
finding-producing analyzers together. The orchestrator coordinates independent
modules; it does not merge their implementations or reinterpret their output.

> v0.9 aggregates existing analysis. It does not reinterpret findings.

> v0.9 introduces no composite severity or aggregate risk score.

> Analyzer failures are reported explicitly and never converted into reassuring
> empty output.

## Architecture

The implementation is deliberately layered:

`orchestrator contract -> explicit analyzer adapters -> deterministic aggregation -> CLI`

Every adapter calls an established analyzer entry point. The composite artifact
uses schema version `0.1`, independently of finding, inventory, change, package,
and report versions. Findings inside it remain finding-schema `0.1` objects.

## Supported adapters

| Analyzer identifier | Explicit input | Existing path | Network boundary |
| --- | --- | --- | --- |
| `directory` | local directory | `audit_directory` then `adapt_directory_finding` | offline |
| `semantic` | local skill file | `evaluate_skill` then `adapt_semantic_violation` | existing model access only |
| `remote` | HTTPS target | `audit_llms_txt` then `adapt_remote_finding` | existing guarded-fetch and registry/DNS behavior |
| `mcp` | captured tools/list JSON | `audit_mcp_tools` then `adapt_remote_finding` | no MCP transport; existing registry/DNS checks only |
| `trust` | saved inventory JSON | `analyze_trust_boundaries` | offline |

Semantic legacy violations have no per-finding severity. Their established
adapter therefore receives the standalone evaluation's existing
`overall_risk` explicitly; the orchestrator does not calculate a new value.

Inventory discovery and inventory comparison are intentionally not adapters in
v0.9. They produce factual inventory/change artifacts rather than
`FindingContract` findings. Their standalone commands remain unchanged.

## CLI and input selection

`semantic-intent audit` uses explicit, repeatable input flags rather than
guessing from one positional argument:

```text
semantic-intent audit --directory ./skill
semantic-intent audit --skill ./skill/SKILL.md
semantic-intent audit --remote https://example.com
semantic-intent audit --mcp ./tools-list.json
semantic-intent audit --trust-inventory ./inventory.json
```

Compatible flags may be combined. Each occurrence receives a stable analyzer
identifier (`remote`, then `remote:2`, for example). `--judge` applies only to
explicit remote and MCP inputs and retains their existing judge semantics.
No discovered content, URL, schema, instruction, capability, or MCP tool is
executed.

## Status and failure semantics

Each requested analyzer has exactly one execution record with one of:

- `success`: analysis completed, including success with zero findings;
- `skipped`: the explicit input was valid but not applicable;
- `failed_invalid_input`: the input or underlying artifact was malformed or
  unsupported;
- `failed_operational`: analysis could not operate or returned an invalid
  canonical finding.

Each record also reports `semantic_coverage` as `not_requested`, `complete`, or
`incomplete`. Existing remote/MCP judge coverage is preserved. A failure in one
adapter does not discard successful findings from another. Failures are status
records, never security findings, risk levels, or empty-success results.

The CLI emits the partial artifact and exits `3` when any analyzer fails. It
exits `0` when all requested analyzers succeed or are explicitly skipped. It
does not derive an exit code from finding severity.

## Deterministic aggregation

Requested analyzers and execution records are ordered by analyzer identifier.
Sourced findings are ordered by:

1. analyzer identifier;
2. finding type;
3. resource (or the empty string);
4. invariant identifier (or the empty string);
5. canonical JSON for the complete finding.

Adapter execution order therefore cannot affect serialization. Findings are
deep snapshots of validated canonical contracts, so later mutation of legacy
results, adapter outputs, or a previous serialized dictionary cannot change the
artifact.

No prose, URL, invariant, or apparent relationship is used for fuzzy
deduplication. If two analyzers emit findings, both are preserved. Exact
duplicates are also retained because no pre-v0.9 cross-analyzer identity exists.

## Standalone/composite equivalence

For each supported analyzer, the composite adapter uses the same established
canonicalization path available to standalone results. After canonical
`FindingContract` serialization, a finding produced independently and through
the composite runner is semantically identical. The composite envelope adds
only the source analyzer identifier and execution status.

Standalone commands and their terminal/JSON reports are not routed through the
orchestrator and remain unchanged: `scan`, `scan-remote`, `scan-mcp`,
`inventory`, `inventory-diff`, and `trust-analyze`.

## Machine-readable artifact

The composite envelope contains only:

- `schema_version`;
- ordered `requested_analyzers`;
- ordered analyzer `executions`;
- ordered sourced `findings`, each containing `analyzer_id` and one canonical
  finding-schema `0.1` object.

Validation rejects unsupported versions, unexpected or missing fields,
duplicate analyzer identifiers, inconsistent execution/finding counts,
unsupported states or coverage values, malformed canonical findings, and
non-JSON or non-finite values. Validation never fills or repairs semantic
fields.

## Explicit non-goals

v0.9 does not add detectors, trust rules, network authority, policy evaluation,
finding reinterpretation, aggregate risk, composite severity, guess-based
deduplication, execution, remediation, or a replacement report format. It does
not change finding schema `0.1`, inventory schema `0.1`, change schema `0.1`,
package/report version `0.4.0.dev0`, or any earlier standalone behavior.
