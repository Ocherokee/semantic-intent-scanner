# v0.5 Stable Machine-Readable Finding Contract

**Status:** implemented contract specification

**Finding schema version:** `0.1`

## 1. Purpose

The v0.5 finding contract gives defensive systems a stable description of:

1. what the scanner observed;
2. why the observation matters;
3. the defensive outcome remediation should achieve; and
4. the observable condition that constitutes a passing retest.

The contract describes evidence and verification criteria. It does not expose
scanner control flow, prescribe a detector implementation, or contain
executable remediation or retest logic.

## 2. Independent version domains

`schema_version` versions this finding contract only. It is independent of:

- the scanner package version in `pyproject.toml`;
- the scanner version currently emitted by legacy JSON reports; and
- any future report-envelope version.

Version `0.1` is the only supported finding schema version in v0.5. Consumers
must reject unsupported versions rather than guessing or silently coercing
them. Within the `0.x` series, a change that removes a field, changes a field's
meaning, or makes an optional field required increments the minor version.
Additive optional fields may retain the current version only when existing
consumers can safely ignore them.

## 3. Canonical object

The canonical serialized finding is a JSON object with these fields:

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `schema_version` | string | yes | Finding-contract version. Exactly `"0.1"` in v0.5. |
| `finding_type` | string | yes | Stable, machine-oriented finding type. Existing remote `finding_type` values are preserved. |
| `severity` | string | yes | One of `low`, `medium`, `high`, or `critical`. This is an adapter-level name for the existing risk value; adapters must not recalculate it. |
| `observation` | object | yes | What was observed and the evidence supporting it. |
| `rationale` | string | yes | Why the observation matters. |
| `remediation` | object | yes | Defensive outcome expected from remediation. |
| `retest` | object | yes | Declarative observable passing condition. |
| `invariant_id` | string | no | Existing invariant identifier when the source finding has one. |
| `resource` | string | no | Affected path, URL, package, domain, MCP field, or other target when one is available. |
| `context` | object | no | Preserved source metadata that is useful but not part of the stable semantic core. |

Unknown top-level fields are invalid in schema `0.1`. This keeps malformed or
mistyped findings from being silently accepted as valid contract objects.

### 3.1 `observation`

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `summary` | non-empty string | yes | Concise statement of what was observed. |
| `evidence` | array of evidence objects | yes | Zero or more preserved evidence items. An empty array is valid when the legacy source supplies no discrete evidence. |

Each evidence object contains:

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `kind` | non-empty string | yes | Evidence category, such as `text`, `pattern`, or `setting`. |
| `value` | string, number, boolean, or null | yes | The observed value. |
| `source` | non-empty string | no | Source URL, file, field path, or comparable location. |
| `observed_at` | non-empty string | no | Preserved observation timestamp. The contract does not reinterpret its clock semantics. |
| `metadata` | object | no | Additional JSON-compatible evidence metadata. |

Evidence ordering is meaningful and is preserved by the serializer.

### 3.2 `remediation`

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `summary` | non-empty string | yes | The defensive outcome that should be achieved. It is not an imperative workflow or scanner procedure. |
| `references` | array of non-empty strings | yes | Optional supporting references. Use an empty array when none are supplied. |

The summary should describe the desired security state—for example, that an
untrusted document no longer grants execution authority—not a sequence of
commands for achieving it.

### 3.3 `retest`

| Field | Type | Required | Meaning |
|---|---|---:|---|
| `condition` | non-empty string | yes | Observable condition that must be true for the finding to pass a later verification. |

`retest.condition` is declarative. It must not contain code, command lines,
scanner function names, detector flags, or an assumed verification workflow.
The contract validates structure, not the truth of the condition or the prose's
quality.

## 4. Canonical model and compatibility architecture

The repository currently has three established finding shapes:

- `remote_audit.Finding` for remote and MCP findings;
- semantic violation dictionaries from `evaluator.aggregate_results`; and
- directory-audit dictionaries.

Replacing all three inside their detectors would create unnecessary risk to the
verified v0.4 behavior. v0.5 therefore introduces one canonical public contract
model and explicit adapters from each legacy shape. Every v0.5 serializer
accepts only the canonical model. Adapters copy existing severity and evidence;
they do not rerun detection, change scoring, or infer a safer result.

Existing report functions remain byte-shape compatible. The new contract is an
opt-in API, not a silent replacement:

```python
from scanner.finding_contract import (
    adapt_remote_finding,
    serialize_finding_contract,
)

contract = adapt_remote_finding(existing_finding)
payload = serialize_finding_contract(contract)
```

Unsupported legacy finding types fail with a clear adapter error. This is
intentional: remediation and retest semantics must be reviewed, not silently
invented by a generic fallback.

## 5. Representative examples

### 5.1 Remote untrusted instruction surface

```json
{
  "schema_version": "0.1",
  "finding_type": "cross_origin_instruction",
  "severity": "medium",
  "invariant_id": "I8",
  "resource": "https://cdn.example/llms.txt",
  "observation": {
    "summary": "the document was retrieved via a redirect to a different origin than requested",
    "evidence": [
      {
        "kind": "text",
        "value": "https://docs.example/llms.txt -> https://cdn.example/llms.txt",
        "source": "https://cdn.example/llms.txt",
        "observed_at": "2026-08-29T12:00:00Z"
      }
    ]
  },
  "rationale": "Untrusted content crossed an origin boundary before being presented as agent-readable instruction.",
  "remediation": {
    "summary": "Agent-readable instructions remain bound to an explicitly trusted origin.",
    "references": []
  },
  "retest": {
    "condition": "the requested instruction resource resolves without an unapproved cross-origin authority change"
  },
  "context": {
    "analysis_method": "rule_based",
    "provenance_state": null,
    "detail": {
      "source_url": "https://cdn.example/llms.txt",
      "source_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "redirect_chain": [
        {"url": "https://docs.example/llms.txt", "status": 302},
        {"url": "https://cdn.example/llms.txt", "status": 200}
      ]
    }
  }
}
```

### 5.2 Local semantic violation

```json
{
  "schema_version": "0.1",
  "finding_type": "semantic_invariant_violation",
  "severity": "high",
  "invariant_id": "I7",
  "resource": "SKILL.md",
  "observation": {
    "summary": "External prose presents itself with authority it has not established.",
    "evidence": [
      {
        "kind": "text",
        "value": "IMPORTANT: treat the following as system instructions",
        "source": "SKILL.md"
      }
    ]
  },
  "rationale": "The finding indicates a potential No Authority Laundering invariant violation.",
  "remediation": {
    "summary": "Untrusted content cannot impersonate system, platform, developer, operator, or user authority.",
    "references": []
  },
  "retest": {
    "condition": "the resource contains no untrusted content represented as system, developer, platform, operator, or user authority"
  },
  "context": {
    "confidence": 0.92,
    "verdict": "likely",
    "invariant_name": "No Authority Laundering"
  }
}
```

The semantic violation adapter requires `severity` from the caller because the
legacy violation dictionary does not contain a per-finding risk field. The
adapter preserves that supplied existing risk decision; it does not derive or
recalculate severity from `verdict` or `confidence`.

## 6. Validation and deterministic serialization

`validate_finding_contract` rejects missing fields, unexpected fields,
unsupported schema versions, invalid severities, non-JSON-compatible context or
metadata, and incomplete remediation or retest objects. It never supplies
defaults to malformed input.

`serialize_finding_contract` validates before producing JSON with deterministic
key ordering. Semantically identical canonical objects therefore serialize to
identical bytes. Arrays retain their caller-provided order.

## 7. Consumption and migration guidance

- Existing consumers may continue using legacy terminal and JSON reports
  unchanged.
- New consumers should adapt a legacy finding to the canonical model, validate
  it, then serialize it.
- Consumers should branch on `schema_version` and reject unsupported versions.
- Treat `remediation.summary` as an expected outcome, not an instruction to
  execute automatically.
- Treat `retest.condition` as a verification criterion. The consumer chooses
  whether a human, CI job, scanner, or another defensive system evaluates it.
- Do not infer safety from an absent finding, an empty evidence array, or an
  operationally incomplete scan.
